# In-match HUD: DOM shape, degrade unit, update cadence, and placeholder ranges

**Context:** Backlog item 004 adds the in-match HUD (lifebars, power bars, round display) driven by `engine`'s live per-tick `MatchState`/`Progress`, on top of the existing canvas-only match scene (`.vibe/decisions/004`). Several concrete choices are needed that neither the brief nor the existing codebase settle on their own: whether the HUD degrades per-field or as a whole, how often it updates relative to the render loop, what accessible shape the bars take, and what "full" means for health/power given neither has a real modeled maximum anywhere in this app yet.

**Decision:**
1. **Plain DOM, not canvas.** The HUD is built once when the match starts (mounted alongside the canvas in `rendering/match-renderer.ts`) and updated by mutating existing nodes' `style.width`/`textContent`/`aria-valuenow`/`aria-valuetext` — never rebuilt or re-created per frame, matching this app's existing no-per-frame-allocation discipline.
2. **Update cadence: once per rendered frame, only on frames that also simulate.** `hud.update(state, progress)` is called from `match-renderer.ts`'s `frame()` right after `drawCurrentState`, only when `computeTicksToRun` reports `ticksToRun > 0` for that frame — never once per simulation tick during a multi-tick catch-up burst, and never on a frame that ticks zero (the HUD then simply keeps its last-drawn values, exactly like the canvas).
3. **Validation is a single all-or-nothing pass per update, one shared degrade unit.** `hud/hud-view-model.ts`'s `deriveHudViewModel` treats `state`/`progress` as `unknown` and either returns a fully valid `HudViewModel` or one error — never a partially-valid model with one bar broken and the other fine. On error, the whole HUD (both players' bars and the round display) swaps to one labeled error region, the same "swap to a sibling error panel" shape `setup/setup-screen.ts`'s `buildErrorState` already establishes — never a silently blank, frozen, or `NaN`-width bar. Match simulation and input handling are entirely unaffected by a HUD-only error: this mirrors `.vibe/decisions/004`'s existing precedent that a round/match outcome never freezes the render loop.
4. **A fighter's own health/power value must be finite and `>= 0` to count as valid** — health/power are never expected to go negative (engine clamps `Power` to `[0, DefaultMaxPower]` itself, and health decrease is a controlled combat effect, never an engine-side negative excursion). A `0` health reading is a normal, valid KO state (full-width-drained bar, `aria-valuetext` reads "0 / 1000"), explicitly distinct from the error region — not visually or structurally confusable with it.
5. **Placeholder maxima, mirroring `.vibe/decisions/004` point 7's existing precedent:** health's max is `rendering/match-config.ts`'s existing `DEFAULT_HEALTH` (1000) — the same placeholder already used as every match's starting health, since `character`'s own data model has no real health total yet. Power's max is a new `MAX_POWER` constant (3000) mirroring `engine`'s own hardcoded `statemachine.DefaultMaxPower` — the WASM `tick`/`newMatch` JSON contract carries each fighter's live `power` value but never its cap, so this app must know the same ceiling independently. Both are documented placeholders, replaced once a real source exists.
6. **Fixed left/right assignment.** Fighter array index 0 (`match.SideP1`) always renders as the left/first HUD player column, index 1 (`SideP2`) as the right/second — never reordered by current health/win standing, so a player's own bar never jumps sides mid-match.
7. **Accessible shape:** each bar is `role="progressbar"` with `aria-valuemin="0"`, a real `aria-valuemax` (1000 or 3000, not a hardcoded 100), a live `aria-valuenow`, and an `aria-valuetext` carrying a human-readable "value / max" string — since this repo has no HUD-specific CSS yet, the numeric text is a primary signal, not decorative. The round/wins block is a separate labeled group from the two player columns. No continuous per-frame `aria-live` chatter: only a one-shot announcement (reusing the scene's existing `aria-live="polite"` region) is fired when the round number or win count actually changes, never on ordinary per-frame health/power updates.
8. **Localized text.** The HUD's own static labels/round text go through this app's existing `t()`/`onLocaleChange` convention, consistent with every other screen — even though `rendering/match-renderer.ts`'s own pre-existing status strings ("Preparing match…", "Match started", the input-status line) are not yet localized. That gap is pre-existing scope creep outside this item, not extended here.

**Reason:** Every point above was raised independently by at least one of the three consulted experts (UI/UX: numeric value alongside fill, no color-only signal, one-shot round-change announcement, distinguishing KO from error; real-time rendering: synchronous write-only update scoped to simulate-only frames, one all-or-nothing validation pass, narrow guard around the HUD call site so a bad HUD payload never touches the tick loop; frontend design: real `aria-valuemax` ranges, fixed side assignment, error region as a structural sibling, KO vs error distinguishability) — grounding each choice in a concrete failure mode rather than an invented default.

**Rejected alternatives:**
- **Per-field/per-bar error degradation** (only the broken bar goes into an error state, everything else updates normally): rejected — flagged by two experts as reading like "the game is buggy" rather than a deliberate degrade, and it complicates the update path for no acceptance-criteria benefit; the brief only requires *a* clear error state, not a partial one.
- **`aria-live` on every HUD update**: rejected — would flood assistive tech with an announcement per combo hit, the most likely accidental regression per the UI/UX consultation; the existing `aria-live` region is reserved for one-shot state changes only (match start, round/win changes).
- **Hardcoded `aria-valuemax="100"` (a plain percentage bar)**: rejected — misreports the real underlying range the moment a real per-fighter health max or a different power cap exists; the real placeholder maxima are used from day one so the accessible contract doesn't need to change later.
