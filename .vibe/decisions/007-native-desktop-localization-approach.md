# Native (Go/SDL2) desktop localization approach: string sourcing, language detection, SDL2 text rendering

**Context:** Backlog item 010 is a scoping-only task, explicitly excluded from roadmap decision `023` ("Adopt i18next as the shared localization approach for every web UI app"), which covers only the DOM-based web build. The native desktop/Android build (Go + `go-gl` + SDL2, decision `022`) is a separate codebase with no DOM, no browser, and no JSON-catalog-loading runtime of the kind i18next uses — it needs its own answer for how it sources translated strings, detects the OS/user's language, and renders non-ASCII text, before any implementation work on it can start. Only English and French are the initially targeted locales, matching the web build's own scope (decision `006` in this repo). No native code exists yet in this repo (only the `go-gl`+SDL2 vs. Ebiten benchmark spike under `benchmarks/render-lang-spike/`) — this decision guides a later, separate implementation backlog item; it makes no code change itself.

**Decision:**

1. **Sourcing translated strings — `go-i18n` v2 (`github.com/nicksnyder/go-i18n/v2`) with per-locale JSON message catalogs, embedded via `go:embed`.** Each locale gets its own catalog file (`locales/en.json`, `locales/fr.json`), the same flat key → string shape the web build's `en.json`/`fr.json` already use (decision `006`), so a contributor moving between the two codebases recognizes the convention even though the two loading mechanisms share no code. Catalogs are compiled into the binary (`go:embed`), never fetched at runtime — the native build ships as an offline, single-file binary per platform with no server, no package installs, and no writable-catalog assumption. A `Bundle` is built once at startup from the embedded files; call sites look up strings through a small typed wrapper (constants or generated identifiers for keys, never raw string literals scattered through call sites) that falls back to the English catalog entry whenever a key is missing from a non-English locale, and appends a build-time check (a small Go test asserting every English key has a French counterpart, run as part of the normal test suite) so a missing translation is caught before release rather than discovered live on the HUD. `go-i18n`'s CLDR-backed pluralization is available if a plural-dependent string is ever needed, without requiring it now.
2. **Language detection — `github.com/jeandeaual/go-locale` at startup, matched against the shipped locale set via `golang.org/x/text/language`.** `go-locale` reads the OS's preferred-language setting (environment variables and defaults on Linux/Mac, the Windows API) into a BCP-47 tag; `language.MatchStrings` (or an equivalent closest-match) resolves it against the two locales actually shipped (`en`, `fr`), falling back to English for anything else (e.g. an OS set to German). Detection runs once at startup; there is no in-app language-override UI in scope for this decision — the acceptance criteria for this item ask only for detecting the OS/user's language "at startup," the same scope boundary decision `006` already drew for a screen that didn't exist yet ("nothing can be extracted from a screen that hasn't been built"; here, nothing can be switched by a settings screen that hasn't been designed). Changing the OS language and relaunching is the only way to change the app's language until a follow-up item designs an in-app override, which this decision explicitly leaves open rather than deciding now. Android detection is deferred to whenever roadmap backlog `010` (the desktop-OpenGL-vs-GLES gap) actually produces a working Android build — `go-locale` does not cover Android today, and there is no Android build to detect a language for yet.
3. **SDL2 text-rendering constraints for English and French — none block French; a font-coverage gate is the only added step.** Text renders through `SDL2_ttf` (`veandco/go-sdl2/ttf`, the same ecosystem as the existing `go-sdl2` benchmark spike) via `TTF_RenderUTF8_Blended` against a single embedded (`go:embed`) OFL-licensed Unicode font (e.g. Noto Sans or DejaVu Sans) confirmed at font-selection time to cover Latin-1 Supplement and Latin Extended-A (é, è, à, ç, ê, œ, ù, â, î, ô, û, ï, ë and the œ ligature) — everything French needs. Rendered glyph textures are cached keyed on `(font, size, color, string content)`, built once when a string first needs to appear (or once at startup for known static labels) and reused every frame, never re-rendered per frame — required to hold the existing no-per-frame-allocation render-loop rule (`CLAUDE.md`'s native rendering performance constraints) — and drawn through the same texture-batching pipeline as any other sprite rather than as a special-cased draw path. No locale needing a non-Latin script (CJK, Arabic, etc.) is currently planned; broader script/font coverage is deferred until such a locale is actually scoped, the same incremental-locale principle roadmap decision `023` already applies to the web build, rather than solved speculatively now.
4. **Scope boundary, stated explicitly:** this decision covers sourcing, detection, and text-rendering constraints only, as the acceptance criteria ask. It does not design an in-app language-switcher UI, does not decide whether a manually-chosen language persists across restarts (there is no manual choice to persist yet), and does not solve Android detection — each is either out of this item's stated scope or blocked on a separate, already-tracked item, and is left for the follow-up implementation backlog item to pick up without needing to re-investigate the three questions this item was asked to answer.

**Reason:** `go-i18n` gives compiled-in, embeddable JSON catalogs with built-in pluralization and no disproportionate code-generation workflow, matching the org's existing preference for a well-solved external library over a bespoke primitive (roadmap decision `023`'s same reasoning, applied to the Go ecosystem's equivalent problem) while keeping the catalog *shape* consistent with the already-shipped web convention. `go-locale` solves cross-platform OS-language detection (a genuinely inconsistent, easy-to-get-subtly-wrong area per this app's real-time-rendering and UI/UX expert consultations) without hand-rolling three platforms' worth of locale APIs. SDL2_ttf plus a verified-coverage Unicode font and a content-keyed glyph cache directly answers the realtime-rendering expert's explicit requirement (no per-frame text-texture allocation, batched draw calls) and confirms French needs nothing beyond a font-selection check — there is no real rendering blocker, only a verification step, exactly the "if none block French, explicitly noted as such" framing the acceptance criteria call for.

**Rejected alternatives:**
- **`golang.org/x/text/message` (with the `gotext` extraction/generation workflow)** — rejected: built for ICU-scale message needs and ships with a heavier code-generation step (extract → generate) disproportionate for a two-locale, largely non-pluralized catalog; `go-i18n`'s direct JSON-file-plus-`Bundle` API fits this app's actual size better, mirroring decision `006`'s own rejection of heavier pluralization machinery for the web build.
- **Hand-rolled `map[locale]map[key]string` literals** — rejected per the data expert consultation: no compile-time protection against a duplicate key silently overwriting another, no built-in pluralization if ever needed, and no natural place to hang a build-time en/fr key-parity check the way a library's own `Bundle`/message-file loading provides.
- **Per-platform hand-written OS-locale detection (raw env vars on Linux/Mac, a direct Windows API call via `golang.org/x/sys/windows`, cgo to `NSLocale` on Mac)** — rejected: exactly the cross-platform inconsistency risk the UI/UX and realtime-rendering consultations flagged; a maintained library purpose-built for this (`go-locale`) removes three bespoke, easy-to-get-wrong implementations for no benefit over adopting it.
- **Deciding an in-app language-override UI or restart-vs-live-switch behavior now** — rejected: not asked for by this item's acceptance criteria (they name only startup detection), and no settings/menu screen exists yet to hang an override on; deciding it now would mean designing UI this decision has no mandate to design, the same reasoning decision `006` used to defer the not-yet-built result screen's strings.
- **Solving Android language detection now** — rejected: no Android build exists yet (blocked on roadmap backlog `010`, the desktop-GL-vs-GLES gap); designing detection for a platform with no runnable target yet risks guessing at constraints that platform's own eventual resolution may change.
