# Visual regression tests serve fixture data through a dedicated Vite config, with a stricter diff threshold

**Context:** Backlog item 011 adds Playwright screenshot-comparison tests for the roster and stage selection screens, extending `web-ui-kit`'s shared visual-testing preset (roadmap decision `024`). Unlike sibling apps that already implemented the same backlog item (e.g. `stage-viewer-web`), this app's roster/stage screens are not driven by an upload UI — they load a deploy-time JSON manifest (`./roster-manifest.json`, `./stage-manifest.json`) fetched at a fixed relative URL when the app boots. The real, committed manifests are intentionally empty (`[]`); a real deployment overwrites them. This meant the sibling "drive the real upload flow with vendored fixture files" approach did not transfer directly — the visual suite needed its own way to get real fixture data in front of the app's own, otherwise-unmodified code.

Separately, while proving this suite's own required "catches a real regression" acceptance criterion, the shared preset's default `maxDiffPixelRatio: 0.02` turned out not to catch a real, deliberate single-button color regression even when the screenshot target was narrowed to one character card (the regression measured ~1.7% of that card's own pixels) — under the shared 2% default.

**Decision:**
1. **Fixture serving:** a dedicated `vite.visual.config.ts` (built via `mergeConfig` over the real `vite.config.ts`, so the two never drift apart on base path/plugins) points `publicDir` at `tests/visual/fixtures/` — committed fixture roster/stage manifests and character/stage files (reusing this repo's existing `src/wasm/testdata/` fixtures plus two small real portrait PNGs) — instead of the real `public/`. The exact same, unmodified `index.html`/`src/main.ts` entry point renders this fixture data for real, through the real `character`/`stage` WASM bridges — no test-only branching in app source. `scripts/prepare-visual-fixtures.mjs` copies the already-downloaded WASM binaries (`public/wasm/`, gitignored, fetched via `npm run wasm:download`/`wasm:download:stage`) into `tests/visual/fixtures/wasm/` before each run, since Vite supports only one `publicDir` per config; it fails fast with a named, actionable error if a source file is missing, rather than silently building without it.
2. **Diff threshold:** this app's `playwright.config.ts` overrides the shared preset's `expect.toHaveScreenshot` to `maxDiffPixelRatio: 0.005` (0.5%), stricter than `web-ui-kit`'s own 2% default, confirmed by measurement to be needed for this app's own compact, information-dense card screenshots.
3. **CI scope:** this repo's first GitHub Actions workflow (`.github/workflows/ci.yml`) runs lint and `npm run test:visual` only. It deliberately does not also run the full `npm test` unit/smoke suite: several of those tests exercise the real `engine` WASM bridge, and `engine`'s GitHub releases currently ship no build asset at all (confirmed via `gh release view`) — an unrelated, pre-existing gap belonging to this repo's own separate `008-release-packaging` backlog item, not fixed here.

**Reason:** The fixture-serving approach keeps the visual suite testing the actual production code path (a real manifest fetch, real WASM parsing) rather than a synthetic bypass, while never touching the real, deploy-specific `public/roster-manifest.json`/`stage-manifest.json`. The stricter threshold was not a guess: the default's insufficiency was directly measured while satisfying this item's own "a real, deliberate rendering regression is caught" acceptance criterion, so shipping the shared default un-overridden would have left that criterion silently unmet. Scoping CI to lint + visual tests only avoids either leaving this item blocked on an unrelated infrastructure gap, or silently expanding its scope into setting up this repo's entire CI/release pipeline.

**Rejected alternatives:**
- **Swap the real `public/roster-manifest.json`/`stage-manifest.json` with fixture content before building, then restore them after**: rejected — mutates real, committed deploy configuration as a side effect of running tests, with real risk of the restore step being skipped on an interrupted run and the wrong content ending up committed.
- **Add a URL-param or env-var branch in `main.ts` to point at a different manifest path during tests**: rejected — introduces test-only conditional logic into the app's own production entry point for a concern the dedicated-Vite-config approach handles with zero source changes.
- **Keep the shared 2% default threshold and instead screenshot only the single changed button element, not the whole card**: considered, but rejected in favor of keeping the screenshot scoped at the card level (a more representative, still-readable baseline unit showing name + portrait + both pick buttons together) with a stricter threshold, rather than fragmenting coverage into many tiny single-element screenshots.
- **Wire the full `npm test` suite into this repo's first CI workflow regardless of the `engine` WASM gap**: rejected — would either fail CI on an unrelated, already-known infrastructure gap this item did not create, or require silently building `engine.wasm` from source in CI (a Go toolchain + sibling-checkout dependency well beyond this item's scope).
