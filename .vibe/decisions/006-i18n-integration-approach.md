# Localization (i18n) integration approach

**Context:** Backlog item 009 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `onLocaleChange`, `<wuik-locale-switcher>`, roadmap decision `023`) so this app's non-match UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads. Two sibling repos (`lifebar-editor`, `lifebar-viewer-web`) already adopted the same shared layer; this app's approach is ported from `lifebar-editor`'s own `.vibe/decisions/009-i18n-integration-approach.md` and adapted to this app's own screens (roster/character selection, stage selection, match setup) and its multi-step selection flow (roster → stage → setup → match, composed by `main.ts`).

**Scope note:** The backlog item's acceptance criteria mention a "round/match result" screen, but that screen does not exist in this codebase yet — it is its own separate backlog item (`007-round-match-result-screen-basic-cpu-opponent`), still `todo`. Nothing can be extracted from a screen that hasn't been built. This item is implemented against the three non-match screens that currently exist (roster selection, stage selection, match setup); the result screen's own strings will move into the catalogs as part of item 007 once it lands, following the same convention established here. This is an autonomous-mode scope resolution (no formal `depends_on` blocks this item — most of its acceptance criteria are independently satisfiable today), not a decision to leave the result screen permanently untranslated.

**Decision:**
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly, under this app's own namespace (`"mode-quick-versus"`) and its own `localStorage` key (`"mode-quick-versus-locale"`, not the shared default — every OpenKakutou app deploys on the same GitHub Pages origin, so sharing the default key would leak one app's language choice into every other one, same reasoning as `lifebar-editor`'s decision 009). Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initAppI18n` has resolved yet — the existing test suite keeps asserting plain English text unchanged.
- `initAppI18n` is only ever called from the real bootstrap (a new `mount()` in `main.ts`), awaited before the first `renderApp` call — never from `renderApp` itself, which stays synchronous so tests can keep calling it directly without bootstrapping i18n at all.
- `<wuik-locale-switcher>` is mounted once in the app shell's toolbar (built once by `renderApp`, never torn down across the roster → stage → setup → match flow, since only `main`'s content is replaced on each screen transition) — not duplicated per screen.
- Live locale-switching is split by how much state a re-render would otherwise destroy, same principle as `lifebar-editor`'s decision 009:
  - Each of the three screens (`roster-screen.ts`, `stage-screen.ts`, `setup-screen.ts`) holds in-progress, not-yet-submitted user selection state in local closures (player 1/2 picks, the chosen stage, the chosen round count/time limit) that a full re-render from scratch would destroy. Each screen therefore subscribes to `onLocaleChange` internally, once per render call, and re-translates only its already-rendered text nodes/labels in place — never rebuilding the DOM or resetting the current selection — unsubscribing the previous call's subscription at the top of the next render on the same root (the same "stop the previous one first" `WeakMap<root, cleanup>` convention `rendering/match-renderer.ts` already uses for its tick loop).
  - `main.ts`'s own transient one-line status/loading/error text (shown briefly between screens while a manifest or match asset fetch is in flight) is translated via `t()` at the moment it is shown, but is not wired to retranslate live if a locale switch happens to land in that exact narrow window — these are not one of the three named screens the acceptance criteria calls out, hold no state a user could lose, and are shown for a few hundred milliseconds in practice. The persistent toolbar itself (title, version, the switcher's own `label` attribute) does retranslate live via one lightweight `onLocaleChange` subscription set up once in `renderApp`, since it stays mounted for the entire session.
- A picked-state checkmark ("✓") is appended in code after a translated label, never embedded inside a catalog string — so a translator touching `roster.player1`/`stage.select` etc. can never accidentally drop or duplicate the glyph.
- The setup screen's round-count option label changes from "3 Rounds" (pluralized noun) to "Rounds: 3" (count first, invariant noun) specifically to avoid needing plural-form catalog entries (`_one`/`_other`) for a value with no product need to say "round" only once — the same pluralization-avoidance choice `lifebar-editor`'s decision 009 already made for its own counts. No test asserts the previous exact wording (only `data-value`/`data-label` attributes are used as test selectors), so this is a safe, non-breaking wording change.
- The setup screen's semantic direction labels ("Up"/"Down"/"Left"/"Right") and the "Controls" heading are translated; the actual bound key/button names shown next to them (`keyLabel(key)`, button names) are not — they name a physical input, not a described action, the same "don't translate a physical control's own name" principle noted by the UX consultation for this item.
- Character and stage names, and any other identifier sourced from character/stage data files rather than this app's own UI chrome, are never translated — only interface text is.

**Reason:** These choices keep the existing test suite passing with minimal, surgical edits (every call site's fallback text matches the prior hardcoded string, or a deliberately and narrowly changed one with no test dependency on the old wording), and specifically avoid the concrete regression a naive "re-render everything on locale change" implementation would introduce here: losing a player's in-progress character/stage/setup picks the instant they switch language.

**Rejected alternatives:**
- *`main.ts` re-invokes each screen's render function wholesale on a locale change* — rejected: these are exactly the screens whose local closure state (both players' picks, the chosen stage, the chosen round/time limit) must not be reset by a language switch, which a wholesale re-render can't tell apart from a first mount.
- *Keep "N Round(s)" pluralized phrasing and add real i18next plural-form catalog keys* — rejected as disproportionate for a fixed, small option set (1/3/5) with no other pluralized string anywhere else in this app; the invariant "Rounds: N" phrasing needs no plural rules at all, and no acceptance criterion or test depends on the old wording.
- *Extract the round/match result screen's strings preemptively, ahead of item 007 building the screen itself* — rejected: there is no screen, code, or text to extract yet; doing so now would mean guessing at UI copy that item 007's own implementation will define.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected for the same cross-app-origin-collision reason `lifebar-editor`'s decision 009 already documents.
