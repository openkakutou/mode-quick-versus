# Round/match result flow, CPU opponent input routing, and the "vs CPU" toggle placement

**Context:** Backlog item 007 closes the core gameplay loop: showing a round/match result and handling rematch/back-to-select, plus a minimal CPU opponent for player 2. `engine`'s `tick()` already reports a `RoundResult` (outcome none/KO/doubleKO/timeout/timeoutDraw + winner) and running `Progress`/`matchOver`/`matchWinner` every call, but recording a round result twice (calling `tick()` again after the outcome is already decided) double-counts the win server-side — `engine` exposes a `resetRound` WASM call (unused until now, per `.vibe/decisions/004` point 1) for the app to explicitly advance to the next round once it decides to. None of this — when/how to freeze, how a player continues, where "vs CPU" lives, how the CPU feeds input — was settled anywhere yet, and several needed a concrete, load-bearing answer neither `engine` nor the existing codebase supplies on their own.

**Decision:**
1. **The render loop fully pauses on a round/match outcome**, rather than only skipping `tick()` calls: once a tick response reports `round.outcome != none`, that frame still resolves sprites/draws the final state and updates the HUD once (so the KO pose is what's frozen), then the loop stops rescheduling `requestAnimationFrame` entirely — not just skipping the `tick()` call — until a round reset resumes it. This is simpler to reason about than a "running but inert" loop and avoids wasted per-frame input reads/HUD updates while frozen.
2. **A round result auto-advances after a fixed delay** (with a visible countdown), no player action required; **a match result requires an explicit Rematch or Back to select action**, no auto-advance. A round result is not a decision point — forcing a keypress between every round of a best-of-5 adds friction for no benefit — while a match result is a real fork the player must choose.
3. **The result overlay renders on top of the frozen last frame** (the canvas keeps its last drawn content, HUD keeps its last values), not a full replacement of the match view — preserves spatial continuity (the KO pose that produced the result stays visible) and avoids standing up a separate screen just to tear it down again on rematch/continue.
4. **Rematch is handled inside `rendering/match-renderer.ts` itself**, by calling `renderMatch(root, input, options)` again with the exact same closure-captured `input`/`options` — the existing "a new call on the same root stops the previous loop first" convention (`activeLoopByRoot`) already does the necessary teardown (closing the old `engine` session, disposing the old input source/HUD) before the fresh match starts. **Back to select is a caller-supplied callback** (`MatchRendererInput.onBackToSelect`) instead, since the rendering module has no business knowing about roster/stage/selection screens; `main.ts` wires it to a new `showRosterSelection(main, options)` helper (factored out of `renderApp`'s own roster-loading tail) that simply redoes roster discovery fresh, rather than threading the already-discovered roster list down through every intermediate screen function just to save one re-fetch on a rare, deliberate user action.
5. **The CPU opponent composes with, rather than replaces, the existing `TickInputSource` abstraction**: `cpu/cpu-input-source.ts`'s `createCpuAwareInputSource` wraps a real base `TickInputSource`, calls its `read()` first (unchanged, still allocation-free), then — only for player 2 — overwrites the same pre-allocated output object in place using `cpu/cpu-controller.ts`'s decision logic, fed a fighter-position observation obtained via a closure the caller supplies at construction time (reading `match-renderer.ts`'s own already-existing `latestFighterStates`), rather than adding an argument to `TickInputSource.read()` itself. This keeps every input source (`keyboard`, `gamepad`, human-combined, CPU-wrapped) satisfying the exact same interface, and costs no extra allocation since the observation getter reads state that already exists and is already updated once per frame.
6. **The CPU controller carries no persisted decision state across calls** — every `decide()` call is a pure function of that call's observation, so there is nothing to reset when a round ends: the loop simply stops calling `read()` at all while frozen (per point 1), and the very next `read()` after a round reset produces a fresh decision from the fresh post-reset positions, with no stale "still holding forward" carryover to guard against separately.
7. **"Vs CPU" is a third radiogroup on the match setup screen** ("Player 2 Control": Human / CPU), **pre-selected to Human** by default — visible and labelled like the existing round-count/time-limit groups (not buried as a per-character roster quirk or an easy-to-miss checkbox), but pre-selected so the existing two-human default flow needs no extra click and no existing Continue-gating logic changes. Selecting CPU also swaps the setup screen's own Controls section for player 2 from the keyboard binding table to a plain "controlled automatically" note, so the choice is reflected right where a player would otherwise look for player 2's keys.
8. **An outcome value `engine` was not expected to produce (an unrecognized round outcome code, an out-of-range winner/matchWinner side) degrades to a "draw" result** — a safe, legible fallback distinguishable from a real player win, rather than leaving the result screen stuck, blank, or throwing. This is the same "resolve to a clear state instead of crashing" precedent `hud/hud-view-model.ts` already set for a malformed WASM payload, applied here to the round/match outcome path instead of the HUD path.

**Reason:** Every point above was raised independently by the UI/UX or real-time-rendering consultation, or is directly forced by `engine`'s own documented contract (`RecordRoundResult` double-counting a repeated tick; `resetRound` already existing and already computing the next round number itself). Grounding each choice in a concrete failure mode or an existing codebase precedent rather than inventing a default.

**Rejected alternatives:**
- **Skip only the `tick()` call while still running the rAF loop** (HUD/input still polled every frame while "frozen"): rejected — does no useful work, and keeps the input source alive to no purpose since nothing reads it during the freeze anyway.
- **A "Continue" button on the round result screen**: rejected per the UX consultation — a round result is not a decision, and requiring a click after every round of a best-of-5 is pure friction; reserved for the match result's real rematch/back-to-select choice.
- **Replacing the whole match view with a dedicated result screen/route**: rejected — loses the KO pose's spatial context for no benefit, and requires standing up and tearing down a whole separate screen just to resume the same canvas/HUD on rematch.
- **Changing `TickInputSource.read()`'s signature to accept live fighter state**: rejected — would force every existing implementation (keyboard, gamepad, every test double) to accept and ignore a parameter they don't need, for the sole benefit of the one CPU-specific caller; a constructor-time closure achieves the same result with zero interface churn.
- **"Vs CPU" on the roster screen (a per-character toggle) or the stage screen**: rejected — neither screen is about match rules/configuration the way the setup screen already is, and a per-card toggle would need to survive both a roster re-render and a rematch, adding state-tracking that the setup screen's existing config object already handles for free.
- **Threading the already-discovered roster/stage lists down through every screen function so "back to select" never re-fetches**: rejected — adds a parameter to every intermediate function for a rare, deliberate user action (backing out of a match), versus one extracted, reused `showRosterSelection` helper that simply redoes the same fetch `renderApp` already does on a fresh load.
