# Match rendering architecture: engine bridge scope, coordinate mapping, compositing, and starting-match defaults

**Context:** Backlog item 005 ("Match Rendering") must composite both fighters' live sprites over the selected stage's layers, continuously driven by `engine`'s live state, with no camera/HUD/input work done yet elsewhere in this app, and several concrete formulas/defaults are needed that neither `engine`'s, `character`'s, nor `stage`'s own docs specify for a *consumer* to invent.

**Decision:**
1. **Engine bridge scope**: the new `wasm/engine-bridge.ts` exposes only `newMatch`/`tick`/`closeMatch` — not `resetRound`. Round-transition flow (deciding when/how to start the next round) is match-flow logic, out of this item's scope (closer to backlog item 007). When a round ends (`round.outcome != none` or `matchOver`), the render loop keeps painting the last simulated frame rather than resetting or freezing with an error.
2. **Client-side frame resolution**: `engine`'s WASM response exposes `animNo`/`animTime` (ticks elapsed since that animation started) but never a resolved frame index (`.vibe/decisions/011`/`012` in `engine`, deliberate). `rendering/animation-resolution.ts` reimplements `engine`'s own Go `currentFrame` algorithm exactly (walk frames' cumulative `time`; `time <= 0` holds forever; wrap via `loopStart` once exhausted) so results never drift from what `engine` itself would show.
3. **Coordinate mapping**: reuses `stage-viewer-web`'s proven convention (`.vibe/decisions/003` there) — stage-space X is horizontally centered (`localCoordWidth/2 + x`), and a fighter sprite's axis (pivot) point is placed at its target position (`start - axis`), using the axis metadata `character`'s own `load()` response already bundles per sprite. Fighter Y (upward-positive, `0` = ground, per `engine/physics`'s own doc comment) maps to canvas Y as `zOffset - y`. **No camera panning in this first cut** — the camera is fixed at the stage's own origin, so a BG element's `delta` (parallax) has no visible scroll effect yet. Documented limitation, not a defect.
   - **Stage BG element sprites draw at `(startX, startY)` as top-left, axis untreated (`0,0`)** — unlike a fighter sprite, a stage sprite's own axis/pivot metadata is not available from `stage`'s `load()` response at all (`Stage` carries only `(group, image)` references, never the referenced `.sff` sheet's own per-sprite metadata); getting the real axis would need a fourth, independent WASM bridge straight to the shared `sff` module's own `load()` (the approach `stage-viewer-web` takes, per its own `.vibe/decisions/003`). Out of scope here: the acceptance criteria ask for correct *ordering*, not pixel-exact placement of every BG element, and this repo's backlog brief names only the `character`+`sff` (bundled) and `stage` WASM builds, not a fourth. A stage whose art was authored with a non-zero sprite axis will render offset from its exact MUGEN position; layering, parallax ratios, and character positioning are unaffected.
4. **Fighter sprite compositing**: horizontal mirroring is `facing === left` XOR `frame.flip` includes `H`; vertical mirroring is `frame.flip` includes `V`. `frame.blend` (additive/subtractive) is not applied — every sprite draws with normal alpha compositing. Both are explicit scope cuts, not oversights.
5. **Placeholder policy**: a fighter or stage element whose sprite reference fails to resolve (missing from the sheet, decode error) always renders the same shared placeholder tile — one visual treatment, not per-source styling. A stage `"anim"` element with no matching `[Begin Action N]` block, or a blank `.air`/animation frame (MUGEN's own "no sprite shown" sentinel), draws nothing — not an error, mirroring the existing distinction `stage-viewer-web` already drew between "not built yet" and "genuinely broken" (`.vibe/decisions/003` there).
6. **Caching discipline**: sprite pixels are decoded once per unique `(sheet, group, image)` for the life of a match session, pre-baked into an offscreen canvas — never re-decoded or re-blitted on a cache hit. Stage BG element draw order (stable sort by `layerNo`) is computed once when the match starts, never re-sorted per tick. Both per the realtime-rendering expert consultation.
7. **Placeholder match-start defaults**: character health totals, gravity, combo window, and input commands are not modeled anywhere yet in this app (or, for health, in `character`'s own read-path data model at all). `rendering/match-config.ts` uses documented placeholder constants (1000 health, 0.5 gravity/tick, a 20-tick combo window, an empty `CommandFile` so no player command is ever recognized — that wiring is backlog item 006's job) until a real source exists. Starting positions are symmetric around the stage center, facing each other; stage boundaries fall back to a fixed range when the stage's own `.def` leaves them unset/invalid (`left >= right`).
8. **Render loop timing**: a fixed-timestep accumulator (60 Hz, matching MUGEN/Ikemen's own tick rate) driven by `requestAnimationFrame`, capped at a maximum number of simulation ticks processed per callback. A tab backgrounded/throttled long enough to exceed that cap **resyncs to wall-clock time** (excess ticks are dropped, the match visibly "jumps forward") rather than running an extended catch-up burst — same clamped-clock precedent as `stage-viewer-web`'s own playback clock (`MAX_DELTA_MS`), chosen over a catch-up burst to avoid a multi-frame freeze on refocus.
9. **`engine` has no published WASM release asset**: unlike `character`/`stage`, `engine`'s latest tag (`v2.1.0`) carries zero release assets — its `.vibe/modules/wasm.md` documents a WASM entrypoint but no repo of its own ever added the release-publishing workflow its two siblings have. Filed as a new `engine` backlog item. This repo's `public/wasm/engine.wasm`/`engine-wasm_exec.js` (gitignored, used for local dev/test) were built directly from the sibling `../engine` checkout in the meantime; `scripts/download-wasm.mjs` gained an `engine` target regardless, ready to fetch a real release once `engine` publishes one.
10. **App wiring**: `main.ts`'s match-setup completion step (previously a static "match is coming soon" message) now starts real match rendering — visual-only, no HUD/input yet, both already tracked as separate backlog items (004, 006) — showing a brief "Preparing match…" status while assets resolve and an `aria-live` announcement once the scene is up, per UX consultation (a canvas-only scene is otherwise silent to assistive tech at the exact moment the app's core view changes).

**Reason:** Every one of these needed a concrete, load-bearing answer to implement anything at all; each is grounded in either `engine`'s own documented Go behavior/doc comments, an already-reviewed sibling pattern (`stage-viewer-web`'s composition ADR), or this item's own expert consultations (realtime-rendering: caching/timing; UI/UX: transitional feedback, placeholder consistency) rather than invented from nothing.

**Rejected alternatives:**
- **Camera follows the action (pans/zooms to keep both fighters in frame)**: rejected for this item — no product decision or acceptance criterion calls for it, and it would need its own coordinate-mapping/clamping design; a fixed camera satisfies every acceptance criterion (position/animation sync, composition ordering, placeholder degradation, frame pacing) without it.
- **Catch-up burst after a backgrounded tab** (run every skipped tick before drawing again, rather than dropping past a cap): rejected — risks a visible multi-frame freeze exactly when the tab regains focus, worse than a one-time visible jump forward.
- **Building `engine.wasm` release publishing directly in this session**: rejected — that is `engine`'s own repo's release-pipeline concern (mirroring `character`/`stage`'s existing workflows), filed there instead of solved by a local workaround baked into this app.
