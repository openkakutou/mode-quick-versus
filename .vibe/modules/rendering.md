# Module: rendering
**Role:** The match scene, once setup is confirmed: composes both fighters' live sprites over the chosen stage's layers, continuously driven by `engine`'s live per-tick state, itself driven by live player input. `match-config.ts` assembles an `engine` `newMatch` request from already-loaded character/stage data, each player's own already-parsed `.cmd` command file, and the setup config (state defs keyed by number, symmetric starting positions clamped to the stage's own boundaries, a stage-boundary fallback, placeholder gameplay constants — health/gravity/combo window — documented in `.vibe/decisions/004`; a fighter's command file falls back to an empty one, per player independently, when none is supplied). `animation-resolution.ts` reimplements `engine`'s own frame-at-elapsed-time algorithm client-side (walking cumulative per-frame time, holding on a non-positive time, wrapping via `loopStart`), since `engine`'s WASM response exposes elapsed time but never a resolved frame index. `scene-composition.ts` is pure coordinate mapping/sprite placement/draw-order logic (no DOM/canvas/WASM): stage-space-to-canvas mapping, a fighter sprite's axis placed at its live position (facing/frame mirroring resolved as an XOR), stage BG elements ordered behind/in front of the fighters by `layerNo`, and placeholder fallback for any sprite reference that fails to resolve — one shared visual treatment, distinct from a reference that legitimately draws nothing (a blank `.air` frame, an `"anim"` BG element with no matching action block). `sprite-pixel-cache.ts` decodes a given sprite reference at most once per match session (one cache instance per sheet — never shared across two different characters' sheets, since `(group, image)` numbering is only unique within one sheet). `tick-scheduling.ts` is the pure fixed-timestep accumulator math capping how many simulation ticks run per rendered frame, dropping the rest of a long backlog rather than running an extended catch-up burst. `match-renderer.ts` ties it together: starts a match via the `engine` bridge, resolves the sprites needed for the current state (cached, batched), reads live input once per rendered frame from `modules/input.md`'s `createTickInputSource` (wrapped by `modules/cpu.md`'s `createCpuAwareInputSource` when player 2 is CPU-controlled) and reuses that same snapshot for every simulation tick the frame's fixed-timestep loop runs (never re-read per tick, keeping the tick hot path allocation-free), and drives the tick loop — a brief "Preparing match…" status while the match starts and initial sprites resolve, then `modules/hud.md`'s HUD (mounted ahead of the canvas, already populated with the match's starting state), a canvas, an `aria-live` announcement once it's up (a canvas-only scene is otherwise silent to assistive tech), a live status line naming each player's current input source (keyboard or gamepad), updated whenever a gamepad connects/disconnects, and (backlog item 007) `modules/result.md`'s round/match result overlay. The instant a `tick()` response reports a decided round, the loop stops calling `tick()` again — even mid catch-up-burst, since a repeated call after the outcome is already decided would double-count the win server-side — finishes that frame's own sprite resolve/draw/HUD update (so the deciding frame is what freezes on screen) and stops rescheduling `requestAnimationFrame` entirely until it resumes. It then shows the round result (auto-continuing to the next round via the `engine` bridge's `resetRound()` once the result's countdown completes, resetting the fixed-timestep accumulator the same way match start seeds it) or, if the match is also over, the match result instead — never both. The match result's "Rematch" restarts a fresh match by calling `renderMatch` again on the same root (the existing "a new call stops the previous loop first" convention already tears down the old session/input source/HUD/overlay); "Back to select" stops the match first, then calls the caller-supplied `onBackToSelect`. The HUD's own `update(state, progress)` is called once per rendered frame that actually simulates (the same cadence as the canvas redraw, never once per tick during a multi-tick catch-up burst), wrapped in a narrow try/catch so a HUD-only failure can never interrupt the tick loop; `stop()` disposes the HUD, the result overlay, and the input source alongside the `engine` session. The real canvas-drawing default bakes each uniquely-resolved sprite's pixels into its own offscreen canvas once (memoized by the pixels array's own identity), `drawImage`s it with a translate/scale transform for flip — never re-baked on a cache hit.
