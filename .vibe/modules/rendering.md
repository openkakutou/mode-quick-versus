# Module: rendering
**Role:** The match scene, once setup is confirmed: composes both fighters' live sprites over the chosen stage's layers, continuously driven by `engine`'s live per-tick state, itself driven by live player input. `match-config.ts` assembles an `engine` `newMatch` request from already-loaded character/stage data, each player's own already-parsed `.cmd` command file, and the setup config (state defs keyed by number, symmetric starting positions clamped to the stage's own boundaries, a stage-boundary fallback, placeholder gameplay constants — health/gravity/combo window — documented in `.vibe/decisions/004`; a fighter's command file falls back to an empty one, per player independently, when none is supplied). `animation-resolution.ts` reimplements `engine`'s own frame-at-elapsed-time algorithm client-side (walking cumulative per-frame time, holding on a non-positive time, wrapping via `loopStart`), since `engine`'s WASM response exposes elapsed time but never a resolved frame index. `scene-composition.ts` is pure coordinate mapping/sprite placement/draw-order logic (no DOM/canvas/WASM): stage-space-to-canvas mapping, a fighter sprite's axis placed at its live position (facing/frame mirroring resolved as an XOR), stage BG elements ordered behind/in front of the fighters by `layerNo`, and placeholder fallback for any sprite reference that fails to resolve — one shared visual treatment, distinct from a reference that legitimately draws nothing (a blank `.air` frame, an `"anim"` BG element with no matching action block). `sprite-pixel-cache.ts` decodes a given sprite reference at most once per match session (one cache instance per sheet — never shared across two different characters' sheets, since `(group, image)` numbering is only unique within one sheet). `tick-scheduling.ts` is the pure fixed-timestep accumulator math capping how many simulation ticks run per rendered frame, dropping the rest of a long backlog rather than running an extended catch-up burst. `match-renderer.ts` ties it together: starts a match via the `engine` bridge, resolves the sprites needed for the current state (cached, batched), reads live input once per rendered frame from `modules/input.md`'s `createTickInputSource` and reuses that same snapshot for every simulation tick the frame's fixed-timestep loop runs (never re-read per tick, keeping the tick hot path allocation-free), and drives the tick loop — a brief "Preparing match…" status while the match starts and initial sprites resolve, then a canvas, an `aria-live` announcement once it's up (a canvas-only scene is otherwise silent to assistive tech), and a live status line naming each player's current input source (keyboard or gamepad), updated whenever a gamepad connects/disconnects. The real canvas-drawing default bakes each uniquely-resolved sprite's pixels into its own offscreen canvas once (memoized by the pixels array's own identity), `drawImage`s it with a translate/scale transform for flip — never re-baked on a cache hit.
