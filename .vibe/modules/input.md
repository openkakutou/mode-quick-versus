# Module: input
**Role:** Live keyboard/gamepad input for both local players, combined into the per-tick `[TickInput, TickInput]` pair `rendering/match-renderer.ts` threads into `engine`'s `tick()` call. `key-bindings.ts` holds the default bindings: two spatially separate keyboard regions (Player 1 WASD-based, Player 2 arrow-key-based, no key ever shared) and the standard Gamepad API button index each of the six MUGEN/Ikemen-GO button names (`a b c x y z`) reads from. `keyboard-input.ts` tracks both players' held keys live via `window` `keydown`/`keyup` listeners into two pre-allocated, mutated-in-place state objects, `preventDefault()`-ing only the keys actually bound to a player, and clearing every held key on `blur` (a `keyup` for an already-held key is not guaranteed to fire once focus returns after e.g. alt-tab, so a stuck-forever held key is avoided proactively). `gamepad-input.ts` polls the Gamepad API and assigns connected pads to players by connection order — never both to the same player — dropping a player back to "no gamepad" the instant their pad reports disconnected, never a stuck/latched button; it never throws even when the Gamepad API itself is absent. `tick-input-source.ts` combines the two: each player has exactly one active source per read — their assigned gamepad if still connected, otherwise their keyboard bindings, never merged — and notifies a caller-supplied callback only when a player's active source actually changes (the visible fallback/reconnect indicator `match-renderer.ts` surfaces). `read()` is meant to be called once per rendered frame; its result (two objects allocated once for the tracker's whole lifetime, mutated in place) is safe to reuse for every simulation tick that frame's fixed-timestep catch-up burst runs, keeping the 60Hz tick hot path allocation-free. See `.vibe/decisions/005-input-routing-design.md`.
