# mode-quick-versus — Codebase index

## Modules
- [`modules/app.md`](modules/app.md) — composition root, builds the app shell (including the locale switcher) and chains the character, stage, then setup screens, then starts match rendering once setup is confirmed; also re-shows character selection when the match result screen's "back to select" fires
- [`modules/wasm.md`](modules/wasm.md) — one bridge per WASM dependency (`character`, `stage`, `engine`), each a typed loader/caller never throwing; `character`/`stage` also expose batched sprite pixel resolution, `stage` also animation frame resolution, `character` also `.cmd` command-file parsing, `engine` also `resetRound` (advancing a decided round to a fresh next round)
- [`modules/roster.md`](modules/roster.md) — roster manifest fetch/validation and per-entry discovery via the character WASM bridge
- [`modules/stage.md`](modules/stage.md) — stage manifest fetch/validation and per-entry discovery via the stage WASM bridge
- [`modules/selection.md`](modules/selection.md) — the roster grid (independent Player 1 / Player 2 picks) and the stage grid (single shared choice), both localized with live in-place re-translation
- [`modules/setup.md`](modules/setup.md) — the match setup screen: independent round-count, time-limit, and Player 2 Control (Human/CPU, pre-selected to Human) radiogroups, gating Continue on the first two, plus a read-only Controls section showing both players' default input bindings (or a "controlled automatically" note for a CPU-driven player 2), localized with live in-place re-translation
- [`modules/input.md`](modules/input.md) — live keyboard/gamepad input for both players, combined into one active source per player per tick (gamepad if connected, else keyboard, never merged), routed into the `engine` bridge
- [`modules/rendering.md`](modules/rendering.md) — the match scene: assembles and starts a real match via the `engine` bridge (including each player's own parsed command file), resolves the sprites needed to draw its live state (cached), reads live input once per frame (or a CPU-driven decision for player 2), drives a fixed-timestep tick loop keeping a canvas — and `modules/hud.md`'s HUD — in sync with the simulation, and freezes on a decided round/match to show `modules/result.md`'s overlay, resuming via `resetRound` or restarting via rematch
- [`modules/hud.md`](modules/hud.md) — the in-match HUD: each player's lifebar and power/meter bar, and the round display (round number, wins, best-of), updated once per simulated frame and degrading as one unit to a clear error state on malformed `engine` match data
- [`modules/result.md`](modules/result.md) — the round/match result overlay: pure outcome derivation from `engine`'s raw round/match codes (degrading an unrecognized outcome to a clear draw rather than an undefined result), and the overlay itself — an auto-advancing countdown for a round result, explicit Rematch/Back to select actions for a match result
- [`modules/cpu.md`](modules/cpu.md) — the minimal, first-pass CPU opponent for player 2: stateless decision logic (walk toward the opponent, occasionally attack in range) composed with the existing input-source abstraction rather than bypassing it
- [`modules/i18n.md`](modules/i18n.md) — this app's own localization setup: the shared `web-ui-kit` i18next integration layer wired under this app's namespace, plus a `t()` wrapper every screen calls to render its own text
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts: downloading a WASM dependency's release build (`character`, `stage`, or `engine` target), and preparing the visual regression suite's own fixture WASM copy

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Every external effect (`fetch`, WASM instantiation, `requestAnimationFrame`) is injected as a parameter with a real default, so every layer is testable under jsdom without a running server — same shape from `wasm/bridge.ts`/`wasm/stage-bridge.ts`/`wasm/engine-bridge.ts` down through `roster/manifest.ts`/`stage/manifest.ts`, `roster/discovery.ts`/`stage/discovery.ts`, `main.ts`'s own `renderApp`, and `rendering/match-renderer.ts`'s own `renderMatch`
- The DOM-building logic of a screen is a pure exported function (`renderApp(root, version, options?)`, `renderRosterScreen(root, entries, options)`, `renderStageScreen(root, entries, options)`, `renderMatch(root, input, options?)`) taking its target element and data/callbacks as parameters, replacing the target's previous content on each call rather than appending
- A render function that can start a background loop (`renderMatch`'s tick loop) registers a stop callback for its root element in a module-level `WeakMap<rootElement, stopFn>`, called and cleared at the top of the next call on that same root, so a previous call's loop never keeps running invisibly once new content replaces it
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs`, not bundled/type-checked by `tsc`
- Fixture-driven tests that exercise a real WASM module use minimal real fixture files (character `.air`/`.sff`/`.cns` copied from `character-viewer-web`'s own test data; the real `stage.wasm`/`stage-wasm_exec.js` and `engine.wasm`/`engine-wasm_exec.js`, both downloaded the same way as `character.wasm` now that `engine` also publishes a release with build assets attached) rather than depending on a sibling checkout at test time
- A result that can fail in an expected way (a WASM load, a manifest fetch, a file fetch) returns a discriminated-union/typed result instead of throwing, so a UI layer can show a clear error state instead of crashing
- One bridge file per WASM dependency rather than a shared/generalized loader — each is an independently released, independently versioned Go program; `wasm/stage-bridge.ts` even keeps its own `wasm_exec.js` on disk (`stage-wasm_exec.js`) rather than reusing `character`'s copy, so the two can never silently drift out of pairing — `wasm/engine-bridge.ts` follows the same convention (`engine-wasm_exec.js`) despite a different call shape (one JSON-encoded request/response per call, rather than typed arguments)
- A single-choice grid (one shared pick, e.g. the stage screen) uses `role="radiogroup"`/`role="radio"`/`aria-checked` and never toggles back to "no selection" on a re-click; an independent-pick grid (one pick per player, e.g. the roster screen) uses plain toggle buttons with `aria-pressed`, since either player's slot can legitimately be empty
- A screen with two independent radiogroups (the setup screen) gives each its own heading wired via `aria-labelledby`, and gates its Continue action on both groups independently rather than a single combined flag
- A screen whose *configured option set itself* can be invalid (not a player input, a deployment/config error) validates it at render time and shows a blocking, named error state instead of falling back to a default selection — distinct from the existing empty-list/empty-roster message, which is a valid "nothing configured" state rather than an error
- Two Go libraries sharing the exact same underlying type (`character`'s and `engine`'s own `character/cns`/`character/air` packages) need no field-mapping code at the TypeScript boundary — a state def or animation array loaded via one WASM module's JSON is forwarded to the other's request unmodified, only reshaped (an array into a keyed map for `map[int]T`'s JSON encoding)
- Two sibling data sources describing the same kind of thing (a fighter's sprite metadata from `character`'s `load()`, a stage's from nowhere at all) aren't assumed symmetric — `character` bundles its sprite sheet's own per-sprite metadata (axis, dimensions) directly in `load()`'s response, but `stage`'s data model only ever carries `(group, image)` references, never the sheet's own metadata; a scope cut (stage elements draw at their configured position, axis untreated) is made explicit rather than reaching for a fourth WASM bridge just for that one field, see `.vibe/decisions/004`
- A `(group, image)` sprite reference is only unique *within* one character's/stage's own sprite sheet — two different characters routinely reuse the same numbering for unrelated sprites, so a lookup/cache keyed by that reference alone is always scoped to one sheet (one cache instance per fighter, one per stage), never merged across sheets even when it would simplify the call site
- A per-sheet resolution cache (`sprite-pixel-cache.ts`) tracks both successful and failed lookups as "already attempted," so a permanently-unresolvable reference is never silently retried every render tick — only genuinely new requests are ever batched into a resolve call, and an empty net-new set makes no call at all
- A fixed-timestep accumulator loop (`tick-scheduling.ts` + `match-renderer.ts`) caps how much simulation catch-up work one rendered frame can do; past the cap the rest of the backlog is dropped and the loop resyncs to wall-clock time (a visible "jump forward") rather than running an extended catch-up burst that risks a multi-frame freeze on tab refocus
- A canvas-only view that changes without any accompanying text (the match scene appearing) pairs an `aria-live` region announcement with the visual change, since a canvas has no DOM content of its own for assistive tech to observe
- A player-facing input with more than one possible device (keyboard vs. a connected gamepad, `input/tick-input-source.ts`) resolves to exactly one active source per player per read, never merged — device assigned by connection order, falling cleanly back to the other device the instant the active one disconnects, with a change callback firing only on an actual switch
- A value naturally sampled once per rendered frame (a gamepad poll, a live input snapshot) is read once per `requestAnimationFrame` callback and reused for every simulation tick that frame's fixed-timestep loop runs — never re-read per tick — the same per-frame (not per-tick) allocation discipline the render loop's own frame-budget rule already applies to drawing
- A named interface (not a plain `Record<string, unknown>`) that must stay assignable to a WASM bridge's own loosely-typed request field (`engine-types.ts`'s `CommandFileBlob`/`TickInput`) carries its own explicit `[key: string]: T` index signature alongside its named fields — TypeScript never infers one from a fixed set of named properties, even when every one of them already matches that type
- A screen holding in-progress, not-yet-submitted state in local closures (both players' roster picks, the chosen stage, the chosen round/time limit) is never wholesale re-rendered on a locale change: each of `roster-screen.ts`/`stage-screen.ts`/`setup-screen.ts` instead subscribes to `i18n.ts`'s `onLocaleChange` internally, once per render call, and re-translates only its already-rendered text nodes in place — unsubscribing the previous call's subscription at the top of the next render on the same root, the same "stop the previous one first" `WeakMap<root, cleanup>` convention `rendering/match-renderer.ts` already uses for its tick loop (now also used by `main.ts`'s own toolbar subscription)
- `i18n.ts`'s `t(key, defaultValue, vars?)` returns the interpolated `defaultValue` verbatim whenever this app hasn't called `initAppI18n` yet in the current page — every call site's `defaultValue` matches its `en.json` entry exactly, so the entire pre-existing test suite kept asserting plain English text with zero changes once screens were switched over to `t()`
- A picked/selected-state checkmark ("✓") is appended in code after a translated label (`roster-screen.ts`'s `setPicked`, `stage-screen.ts`'s `setSelected`), never embedded inside a catalog string, so a translator touching the base label can never accidentally drop or duplicate the glyph
- A UI label describing what a control *does* (`setup-screen.ts`'s "Up"/"Down"/"Left"/"Right" direction labels, the "Controls" heading) is translated; the actual physical key/button name shown next to it (`keyLabel(key)`, the six MUGEN/Ikemen-GO button names) is not — it names a physical input, not a described action
- An installed dependency whose `package.json` "exports" points only at built JS/CSS (`@openkakutou/web-ui-kit`) breaks `tsc` the moment a *named* import is used (`initI18n`, `getI18n`, ...), even though it works fine at runtime/Vitest — fixed with a scoped ambient `declare module` (`src/types/web-ui-kit.d.ts`) typing only what this app actually imports by name, the same gap and fix already applied by the sibling `lifebar-editor`/`lifebar-viewer-web`/`stage-viewer-web` repos
- The visual regression suite (backlog item 011) serves real committed fixture data through a *second*, dedicated Vite config (`vite.visual.config.ts`, built via `mergeConfig` over the real `vite.config.ts`) whose `publicDir` points at `tests/visual/fixtures/` instead of the real `public/` — needed because this app's roster/stage screens fetch a fixed-URL deploy-time manifest rather than accepting an upload, unlike sibling apps' own visual-regression suites; the exact same, unmodified `index.html`/`main.ts` entry renders the fixture data for real. See `.vibe/decisions/008`
- `web-ui-kit`'s shared visual-testing preset's default `maxDiffPixelRatio` (0.02) is overridden stricter (`0.005`) in this app's own `playwright.config.ts` — confirmed by direct measurement that a real single-button color regression sits under the shared default even scoped to one character card's own screenshot. See `.vibe/decisions/008`
- A Playwright `webServer` step that rebuilds a fixture-only bundle needs its own prep script run first when the fixture assets live outside the app's real `public/` (`scripts/prepare-visual-fixtures.mjs` copying `public/wasm/` into `tests/visual/fixtures/wasm/`, itself gitignored and regenerated every run) — failing fast with a named error naming the missing source file and which `npm run wasm:download*` command to run, rather than silently building without it
- A value read every simulation tick but only ever meaningful once per rendered frame (`hud/hud-renderer.ts`'s `update(state, progress)`) is called from the same `if (ticksToRun > 0)` branch that already gates the canvas redraw — never once per tick during a multi-tick catch-up burst — and wrapped in its own narrow `try`/`catch` at the call site so a HUD-only defect can never propagate into `stop()`/the tick loop, the same "a display concern never touches simulation" boundary `.vibe/decisions/004` already drew for a round/match outcome
- A validator for data crossing a WASM JSON boundary (`hud/hud-view-model.ts`'s `deriveHudViewModel`) treats the decoded payload as `unknown` and fails the *whole* derivation on any single invalid field, never returning a partially-valid result — `engine-bridge.ts`'s own `parseEnvelope` only type-asserts the JSON, it never validates it, so runtime shape mismatches are only ever caught by a downstream consumer choosing to validate, not by the bridge itself
- An accessible range control whose real range isn't `[0, 100]` (`hud/hud-renderer.ts`'s health/power bars) sets `aria-valuemin`/`aria-valuemax` from the actual underlying cap (the app's own placeholder health/power maxima) plus an `aria-valuetext` carrying a human-readable "value / max" string, rather than assuming a plain percentage bar — paired with a visible value-text span, since this repo has no HUD-specific CSS yet and the numeric text is a primary signal, not decorative
- A per-frame-updated `aria-live` region (`hud/hud-renderer.ts`'s round/win announcement) fires only on an actual state change (the round number or a win count), tracked against the last announced value, never on every ordinary numeric update in between — the same "don't spam assistive tech every tick" restraint already applied to the match-renderer's own per-frame input-status line, now stated as a first-class rule for any per-frame-driven live region
- A placeholder gameplay constant that mirrors an upstream Go package's own hardcoded value but isn't itself part of that package's WASM JSON contract (`match-config.ts`'s `MAX_POWER`, mirroring `engine`'s `statemachine.DefaultMaxPower`) is defined once, next to this app's other placeholder constants (`DEFAULT_HEALTH`, `DEFAULT_GRAVITY`), rather than re-derived or hardcoded again at each call site
- A fixed-timestep catch-up burst that discovers a terminal per-tick condition mid-loop (`match-renderer.ts`'s `runTicks` hitting a decided `RoundResult`) breaks immediately rather than finishing the frame's remaining iterations — calling `engine`'s `tick()` again after an outcome is already decided would double-count that round's win server-side (`round.Progress.RecordRoundResult`), so "stop the instant it's true" is load-bearing correctness here, not just an optimization
- A render loop pausing for a real player-facing wait (`match-renderer.ts` freezing on a round/match result) stops rescheduling its own `requestAnimationFrame` entirely rather than continuing to run "inert" frames that skip only the expensive part — cheaper to reason about (the loop is either running or it isn't) and avoids wasted per-frame input/HUD work with nothing new to show
- A one-shot, non-decision player-facing pause auto-advances on a timer with a visible countdown (`result/result-screen.ts`'s round result); a genuine fork in what happens next always requires an explicit action (its own match result's Rematch/Back to select) — never the reverse, and never both on the same screen
- A secondary AI-driven input source composes with the primary human one instead of replacing or special-casing it (`cpu/cpu-input-source.ts` wrapping a real `TickInputSource`, mutating only its own player's slot in the same pre-allocated pair) — every caller downstream keeps seeing one ordinary input source, and the human player's own slot is never touched
- Live per-frame state an AI decision needs (`cpu/cpu-controller.ts`'s fighter positions) is threaded in via a closure supplied at the AI wrapper's construction time, reading state the render loop already tracks — never by adding a parameter to the shared interface's own per-frame read method, which would force every other implementation (and every test double) to accept and ignore it
- A third configuration radiogroup added alongside two existing required ones (`setup-screen.ts`'s Player 2 Control, next to round count/time limit) is pre-selected to its default value rather than left unselected like its siblings, specifically so it never gates the existing Continue action or adds a click to the established two-human flow — unselected-by-default is reserved for a field with no safe default to assume
- Restarting the exact same operation from scratch (`match-renderer.ts`'s own "Rematch") is done by the module calling its own already-idempotent entry point again on the same target (`renderMatch(root, input, options)`), reusing the existing "a new call stops the previous instance first" convention, rather than hand-rolling a second, parallel reset code path
- A rare, deliberate user action that could reuse already-fetched data (`main.ts`'s "back to select" re-showing character selection) instead re-fetches fresh through the same helper the initial load already uses (`showRosterSelection`), rather than threading the already-discovered list down through every intermediate screen function just to save one fetch on a path a player takes at most a few times per session
