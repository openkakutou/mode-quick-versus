# mode-quick-versus — Codebase index

## Modules
- [`modules/app.md`](modules/app.md) — composition root, builds the app shell and chains the character, stage, then setup screens, then starts match rendering once setup is confirmed
- [`modules/wasm.md`](modules/wasm.md) — one bridge per WASM dependency (`character`, `stage`, `engine`), each a typed loader/caller never throwing; `character`/`stage` also expose batched sprite pixel resolution, `stage` also animation frame resolution, `character` also `.cmd` command-file parsing
- [`modules/roster.md`](modules/roster.md) — roster manifest fetch/validation and per-entry discovery via the character WASM bridge
- [`modules/stage.md`](modules/stage.md) — stage manifest fetch/validation and per-entry discovery via the stage WASM bridge
- [`modules/selection.md`](modules/selection.md) — the roster grid (independent Player 1 / Player 2 picks) and the stage grid (single shared choice)
- [`modules/setup.md`](modules/setup.md) — the match setup screen: independent round-count and time-limit radiogroups, gating Continue on both, plus a read-only Controls section showing both players' default input bindings
- [`modules/input.md`](modules/input.md) — live keyboard/gamepad input for both players, combined into one active source per player per tick (gamepad if connected, else keyboard, never merged), routed into the `engine` bridge
- [`modules/rendering.md`](modules/rendering.md) — the match scene: assembles and starts a real match via the `engine` bridge (including each player's own parsed command file), resolves the sprites needed to draw its live state (cached), reads live input once per frame, and drives a fixed-timestep tick loop keeping a canvas in sync with the simulation
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading a WASM dependency's release build (`character`, `stage`, or `engine` target)

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Every external effect (`fetch`, WASM instantiation, `requestAnimationFrame`) is injected as a parameter with a real default, so every layer is testable under jsdom without a running server — same shape from `wasm/bridge.ts`/`wasm/stage-bridge.ts`/`wasm/engine-bridge.ts` down through `roster/manifest.ts`/`stage/manifest.ts`, `roster/discovery.ts`/`stage/discovery.ts`, `main.ts`'s own `renderApp`, and `rendering/match-renderer.ts`'s own `renderMatch`
- The DOM-building logic of a screen is a pure exported function (`renderApp(root, version, options?)`, `renderRosterScreen(root, entries, options)`, `renderStageScreen(root, entries, options)`, `renderMatch(root, input, options?)`) taking its target element and data/callbacks as parameters, replacing the target's previous content on each call rather than appending
- A render function that can start a background loop (`renderMatch`'s tick loop) registers a stop callback for its root element in a module-level `WeakMap<rootElement, stopFn>`, called and cleared at the top of the next call on that same root, so a previous call's loop never keeps running invisibly once new content replaces it
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs`, not bundled/type-checked by `tsc`
- Fixture-driven tests that exercise a real WASM module use minimal real fixture files (character `.air`/`.sff`/`.cns` copied from `character-viewer-web`'s own test data; the real `stage.wasm`/`stage-wasm_exec.js`, downloaded the same way as `character.wasm`; `engine.wasm` built locally from a sibling checkout since it has no published release yet) rather than depending on a sibling checkout at test time
- A result that can fail in an expected way (a WASM load, a manifest fetch, a file fetch) returns a discriminated-union/typed result instead of throwing, so a UI layer can show a clear error state instead of crashing
- One bridge file per WASM dependency rather than a shared/generalized loader — each is an independently released, independently versioned Go program; `wasm/stage-bridge.ts` even keeps its own `wasm_exec.js` on disk (`stage-wasm_exec.js`) rather than reusing `character`'s copy, so the two can never silently drift out of pairing — `wasm/engine-bridge.ts` follows the same convention (`engine-wasm_exec.js`) despite a different call shape (one JSON-encoded request/response per call, rather than typed arguments)
- A single-choice grid (one shared pick, e.g. the stage screen) uses `role="radiogroup"`/`role="radio"`/`aria-checked` and never toggles back to "no selection" on a re-click; an independent-pick grid (one pick per player, e.g. the roster screen) uses plain toggle buttons with `aria-pressed`, since either player's slot can legitimately be empty
- A screen with two independent radiogroups (the setup screen) gives each its own heading wired via `aria-labelledby`, and gates its Continue action on both groups independently rather than a single combined flag
- A screen whose *configured option set itself* can be invalid (not a player input, a deployment/config error) validates it at render time and shows a blocking, named error state instead of falling back to a default selection — distinct from the existing empty-list/empty-roster message, which is a valid "nothing configured" state rather than an error
- Two Go libraries sharing the exact same underlying type (`character`'s and `engine`'s own `character/cns`/`character/air` packages) need no field-mapping code at the TypeScript boundary — a state def or animation array loaded via one WASM module's JSON is forwarded to the other's request unmodified, only reshaped (an array into a keyed map for `map[int]T`'s JSON encoding)
- Two sibling data sources describing the same kind of thing (a fighter's sprite metadata from `character`'s `load()`, a stage's from nowhere at all) aren't assumed symmetric — `character` bundles its sprite sheet's own per-sprite metadata (axis, dimensions) directly in `load()`'s response, but `stage`'s data model only ever carries `(group, image)` references, never the sheet's own metadata; a scope cut (stage elements draw at their configured position, axis untreated) is made explicit rather than reaching for a fourth WASM bridge just for that one field, see `.vibe/decisions/004`
- A `(group, image)` sprite reference is only unique *within* one character's/stage's own sprite sheet — two different characters routinely reuse the same numbering for unrelated sprites, so a lookup/cache keyed by that reference alone is always scoped to one sheet (one cache instance per fighter, one per stage), never merged across sheets even when it would simplify the call site
- A per-sheet resolution cache (`sprite-pixel-cache.ts`) tracks both successful and failed lookups as "already attempted," so a permanently-unresolvable reference is never silently retried every render tick — only genuinely new requests are ever batched into a resolve call, and an empty net-new set makes no call at all
- A fixed-timestep accumulator loop (`tick-scheduling.ts` + `match-renderer.ts`) caps how much simulation catch-up work one rendered frame can do; past the cap the rest of the backlog is dropped and the loop resyncs to wall-clock time (a visible "jump forward") rather than running an extended catch-up burst that risks a multi-frame freeze on tab refocus
- A canvas-only view that changes without any accompanying text (the match scene appearing) pairs an `aria-live` region announcement with the visual change, since a canvas has no DOM content of its own for assistive tech to observe
- A player-facing input with more than one possible device (keyboard vs. a connected gamepad, `input/tick-input-source.ts`) resolves to exactly one active source per player per read, never merged — device assigned by connection order, falling cleanly back to the other device the instant the active one disconnects, with a change callback firing only on an actual switch
- A value naturally sampled once per rendered frame (a gamepad poll, a live input snapshot) is read once per `requestAnimationFrame` callback and reused for every simulation tick that frame's fixed-timestep loop runs — never re-read per tick — the same per-frame (not per-tick) allocation discipline the render loop's own frame-budget rule already applies to drawing
- A named interface (not a plain `Record<string, unknown>`) that must stay assignable to a WASM bridge's own loosely-typed request field (`engine-types.ts`'s `CommandFileBlob`/`TickInput`) carries its own explicit `[key: string]: T` index signature alongside its named fields — TypeScript never infers one from a fixed set of named properties, even when every one of them already matches that type
